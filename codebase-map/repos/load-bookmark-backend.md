# load-bookmark-backend

## What it is
Quarkus 3.27.5 / Java 21 service that **manages carrier-side load bookmarks** ("saved for later"). Subscribes to a carrier-TMS Pub/Sub subscription for posting (`LoadDto`) and vehicle (`VehicleDto`) events and keeps each user's bookmarks in sync with the underlying load/vehicle state (including marking bookmarks expired). Exposes REST CRUD under `/v1` and `/v2` plus an action endpoint, and pushes bookmark-change events out as WebSocket notifications. Java/JVM counterpart to the Python `load-bookmark-service` — see Don't-do-here for the boundary question.

## How it fits
- Consumes API of: a **postings impersonator** endpoint via `cars.ship.cube.client.PostingsImpersonatorClient` (built over `WebClientImpl`), pointed at `loadbookmark.config.impersonator-service-url`. **No connect/read timeouts** — `WebClientImplConfig` builds a bare `WebClientImpl` with no timeout options.
- Publishes events to: WebSocket notifications via `NotificationClient` (`quarkus-notification-client`) — `sendWebSocket(...)` to per-user rooms; these flow through the notification topic (`ship.cars.notification.topic`) consumed downstream by pusher / socket-server. There is **no direct domain-event Pub/Sub publish** from this service.
- Subscribes to: the carrier-TMS subscription (`loadbookmark.config.carrier-tms-subscription`, e.g. `…carrierlb.events-load-bookmark…`) via `PlatformEventsListener` (`PubSubConsumerBlocking<MessageObjectDto>`).
- Owns data store: PostgreSQL (`quarkus.datasource.jdbc.max-size=4` in prod; 16 in `%dev`). `schema-management.strategy=none` — Flyway owns schema. **Prod pool size 4 is dangerously small** — see Don't-do-here.

## Key abstractions
- `V1BookmarkResource` / `V2BookmarkResource` / `ActionResource` — `resources/.../rest/{v1,v2,}/…` — REST CRUD endpoints (v1 + v2 coexisting) plus an action resource.
- `PlatformEventsListener` — `services/.../listeners/PlatformEventsListener.java` — `PubSubConsumerBlocking<MessageObjectDto>`; routes posting vs. vehicle messages via `Is*ObjectTypeSpecification`, then **synchronously** calls `BookmarkService.syncLoadWithBookmarks()` / `syncVehicleWithBookmarks()`.
- `BookmarkChangeListener` — `services/.../handlers/BookmarkChangeListener.java` — `@ConsumeEvent(BOOKMARK_UPDATED, blocking=true)` on the in-process Vert.x event bus; hands off to a `ManagedExecutor` that calls `NotificationClient.sendWebSocket(...)`.
- `PostingClientProvider` / `WebClientImplConfig` — `services/.../config/…` — CDI producers for `PostingsImpersonatorClient` and the shared `WebClientImpl`.

## Don't-do-here / gotchas
- **HikariCP pool size 4 in production** (`quarkus.datasource.jdbc.max-size=4`) — extreme outlier vs. fleet norm of 16–20; dev overrides to 16. Under any concurrent burst (posting events + REST traffic) this saturates immediately. Likely a copy-paste oversight; raise it.
- **Blocking Pub/Sub consumer + timeout-less impersonator call** — `PlatformEventsListener.consume()` runs synchronously and can reach `PostingsImpersonatorClient` (no connect/read timeout). A slow upstream stalls the consumer until the Pub/Sub ACK deadline fires and the message redelivers; combined with pool=4 this can lock the service.
- **No REST-client timeouts** — bare `WebClientImpl` (`WebClientImplConfig`); same fleet anti-pattern (retry/wait with no timeout).
- **Schema management `none`** — Flyway is the only path; out-of-band schema drift between dev and prod is plausible.
- **Two REST API versions live** (`v1` + `v2`) — have a deprecation plan or this is permanent.
- **Boundary with `load-bookmark-service` (Python) is unclear** — both manipulate "bookmarks." Which is source of truth vs. sidecar? Worth a 1-page note.
