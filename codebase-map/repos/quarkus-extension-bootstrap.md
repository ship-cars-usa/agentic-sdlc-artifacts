# quarkus-extension-bootstrap

## What it is
A **template repo for creating new Ship.Cars Quarkus extensions** — not a usable extension itself. Per the README:

> Search for `Extension-Bootstrap` and `extensions.bootstrap` and `extension-bootstrap` and replace with the extension name.

So when a Ship.Cars engineer wants to write a new Quarkus extension (e.g. a new typed REST-client wrapper or a new SPI integration), they clone this repo and find-and-replace the bootstrap name. The minimal surface — `BootstrapDto` and `BootstrapConfig` — illustrates:
- How a config class is wired (`BootstrapConfig.java` shows the `@ConfigMapping` pattern).
- How to register classes for reflection at deployment time (per README: "Look at `QuarkusExtensionsBootstrapProcessor.java` to see how classes are registered for reflection").

Versioned `1.0.0-SNAPSHOT` (vs. the fleet's typical `3.27.x` pinning) — confirming it's not deployed and not on the BOM cadence.

Last commit 2025-10-10 (`CORE-000 Cleanup`).

## How it fits

- **Not a runtime extension.** Don't depend on `ship.cars.quarkus.extensions.bootstrap` from a real service.
- **Influence-only:** new Ship.Cars Quarkus extensions are scaffolded from this. Counterpart to `quarkus-imperative-boilerplate` and `quarkus-k8s-boilerplate` (service templates) on the **extension** side.
- **No fleet consumers** by design (it would be a mistake to import it).

## Build / test / run
```
./mvnw clean install -DskipTests
./mvnw test
# But the primary "build" is conceptual:
# 1. Clone the repo to a new repo name (e.g. quarkus-extension-my-feature).
# 2. Find-and-replace Extension-Bootstrap / extensions.bootstrap / extension-bootstrap.
# 3. Add real config + real runtime classes + real deployment processor.
# 4. Publish from the new repo, not this one.
```

## Key abstractions

- **`runtime/.../BootstrapDto.java`** — illustrative DTO (the "this is where your DTOs go" example).
- **`runtime/.../config/BootstrapConfig.java`** — illustrative `@ConfigMapping` (the "this is where your config goes" example).
- **`deployment/.../QuarkusExtensionsBootstrapProcessor.java`** (per README; not directly verified at this depth) — the deployment-time processor showing how to register classes for native-image reflection.

## Don't-do-here / gotchas

- **Don't import this repo into a real service.** It's a template; doing so would import the placeholder `BootstrapDto` / `BootstrapConfig` into your runtime — useless at best, confusing at worst.
- **Updates here don't propagate.** Like the imperative + k8s boilerplates, updates to this template don't auto-merge into derivative extensions. Each existing extension was forked at a particular point; new conventions land via hand-merge or by re-cloning + re-implementing.
- **`1.0.0-SNAPSHOT`** signals it's frozen at v1; don't expect ongoing version bumps tracking the Quarkus platform.
- **No documented derivative extensions.** It's likely that `quarkus-extension-webclient`, `quarkus-extension-persistence`, `quarkus-extension-media-proxy`, `quarkus-pubsub`, `quarkus-locationprovider-client`, `quarkus-auto-reflection`, `quarkus-request-filter` were all bootstrapped from this template — the shared "multi-module (runtime + deployment + coverage-report)" layout suggests as much — but no commit history confirms.
