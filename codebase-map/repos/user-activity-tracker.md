# user-activity-tracker

## What it is
Quarkus 3.27.5 / Java 21 **high-throughput event-ingestion + analytics** service ("UATS"). Accepts user-behavior events via REST `POST /api/events` and Google Pub/Sub, deduplicates with SHA-256 hashing, persists to PostgreSQL, maintains Redis HyperLogLog for real-time unique counts (30-day TTL), and exports archived events as **Parquet to GCS** (BigQuery downstream). Provides REST analytics queries: unique users, active-user time-series, event distribution, entity leaderboards. Pure data-platform service; not in the request path of any business workflow. **Re-domained from `identity` to `analytics`** in this pass — events tracking + Parquet/BigQuery export is analytics, not identity.

## How it fits
- Consumes API of: none (internal-only).
- Publishes events to: none external; internally publishes to its own Pub/Sub topic from the REST endpoint to be consumed by its own listener (REST → Pub/Sub → listener → PG + Redis).
- Subscribes to: Pub/Sub `useractivitytracker.internal-subscription` via `UserActivityTrackerListener` implementing `PubSubConsumerBlocking<EventDto>`.
- Owns data store: **PostgreSQL** (Panache, Flyway, dev `jdbc.max-size=16`); **Redis** (HyperLogLog, `max-pool-size=10000`); **GCS** (Parquet archive bucket via `USER_ACTIVITY_TRACKER_GCS_BUCKET`).

## Key abstractions
- `EventResource` — `/api/events` — REST POST for event ingestion (returns 202).
- `UserActivityTrackerListener` — Pub/Sub consumer; routes to `EventProcessingService`.
- `EventProcessingService` — SHA-256 dedup, Redis HLL update, transactional PG write.
- `AnalyticsService` — query path: short-window queries via Redis, historical via PG.
- `ParquetExportService` / `ParquetWriterService` — periodic / on-demand GCS Parquet export.
- `ParquetExportResource` — REST trigger for ad-hoc export.

## Don't-do-here / gotchas
- **Redis `max-pool-size=10000`** — extreme outlier; either deliberately high for QPS or a misconfiguration. Connection churn at that scale is its own issue. Confirm against production metrics.
- **Dual-write PG + Redis** — Redis is acceptable to lose for analytics (HLL is approximate by design); however the **1-hour TTL on dedup keys** is the actual correctness mechanism. If Redis is wiped, duplicate events can land in PG. The 30-day HLL TTL is fine.
- **No ShedLock on Parquet export** — concurrent exports across replicas could corrupt GCS files (overlapping objects, partial writes). Lock the export job.
- **Hadoop client 3.3.6 bundled** for Parquet writing — heavy dependency, native-image build classpath needs verification; multiple historically-CVE-prone transitives (commons-cli, etc.). Exclude what you can.
- **Pub/Sub subscription misconfiguration silently fails** — if `USER_ACTIVITY_TRACKER_INTERNAL_SUBSCRIPTION` is unset, the listener doesn't start and there's no startup health-check that blocks the pod. Add a startup readiness gate.
- **GCS bucket env var has no fallback** — missing var → NPE on first export.
- **SHA-256 dedup is in-process** — collision probability is irrelevant; the issue is that two pods receiving the same event before either writes will both consider it new. PG's primary key on `(event_hash)` is the actual idempotency mechanism — confirm the index exists.
- **No backpressure on the REST endpoint** — `POST /api/events` returns 202 immediately and queues into Pub/Sub. Sustained burst overload pushes the cost onto Pub/Sub quota.
