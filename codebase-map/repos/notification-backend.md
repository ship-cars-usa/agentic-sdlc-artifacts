# notification-backend

## What it is
Multi-channel notification delivery service. Spring Boot 3.2.12. Consumes notification events from Pub/Sub and routes to email (SendGrid), SMS (Twilio), push (Firebase), or WebSocket (in-app). Resolves user details via `user-backend`. Mostly event-driven — does **not** validate JWTs (Keycloak disabled in config). Does not own final delivery; enqueues to downstream channel SDKs. The `notification-orchestrator` (Quarkus) handles complex multi-step workflows separately.

## How it fits
- Consumes API of: `user-backend` via `WebClient` (commons-derived) — `GET /internal/v2/users/{userExternalId}`, base URL = `${config.usermanagement.base-url}`. Wrapped in timer metric `notification.user_management.requests`.
- Publishes events to: GCP Pub/Sub `notification` topic (no transactional outbox observed).
- Subscribes to: GCP Pub/Sub subscriptions `notification-state` (inbound notifications), `user-state`, `loadboard-state`.
- Owns data store: PostgreSQL — minimal schema (TokenInfo + a User cache); Spring Data Envers wired.

## Key abstractions
- `NotificationConsumer` — `notification-app/src/main/java/cars/ship/shipperlite/notification/application/adapters/in/pubsub/NotificationConsumer.java` — main Pub/Sub listener; **acks AFTER processing** — including in the catch block (`line 126`) — see gotchas. Records per-message metrics. Logs warning if message age exceeds `log-warning-on-processed-after-publish-time-ms` (30 s default).
- `NotificationFacadeImpl` — `notification-app/.../in/pubsub/facade/impl/NotificationFacadeImpl.java` — type-router; switches on `WEBSOCKET | EMAIL | PUSH | PUSH_V2 | SMS` and delegates. Throws `IllegalArgumentException` on unknown type.
- `EmailNotificationServiceImpl` — `notification-app/.../domain/service/EmailNotificationServiceImpl.java` — calls `emailClient.sendEmail()`; logs warn if zero receivers.
- `UserManagementClientImpl` — `notification-app/.../application/adapters/out/clients/UserManagementClientImpl.java` — outbound to `user-backend`.
- `TokenStateConsumer`, `UserStateConsumer` — consume token / user-presence updates.
- `PushNotificationResendService` (port) — Firebase resend queue.

## Don't-do-here / gotchas
- **HikariCP `maximum-pool-size=5` HARDCODED** in `application.properties:96`, no env override. Same alarming setting flagged in the fleet review for `chat-backend`. Probably acceptable for a mostly-event-driven workload but confirm under SLO; treat any pool-saturation metric as a P1.
- **Silent ack on exception (P0)** — `NotificationConsumer.java:126`: if `notificationFacade.handleNotification()` throws, the exception is caught, logged, and the message is **still acked**. Failed notifications are dropped. No retry, no DLQ. Idempotency on the *delivery* side (SendGrid/Firebase have idempotent endpoints) is the only safety net. Recommended fix: either nack-and-redeliver or route exceptions to a Pub/Sub dead-letter topic.
- **Retry config exists but only for `user-backend` lookups** — `max-retries=7`, capped backoff 1750 ms. Does **not** apply to Pub/Sub processing itself.
- **Keycloak disabled** — `application.properties:13: keycloak.enabled=false`. No JWT validation. Trust model: GCP IAM on the Pub/Sub topic.
- **Channel handlers are synchronous, imperative** — no Spring Integration flow; if SendGrid or Firebase hangs, the entire message-processing thread blocks (GCP deadline ~90 s per `application.properties:134` comment).
- **Testing-mode flag** — `config.testing-mode.enabled` (referenced at `NotificationConsumer.java:75`); when true, *all* messages are acked without processing. Critical that this is not accidentally on in production.
- **Stale `CLAUDE.md`** — references general dev rules, no architecture notes.

## Relevant ADRs / docs
- `README.md` — quick-start only, no architecture notes.
