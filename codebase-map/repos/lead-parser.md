# lead-parser

## What it is
Legacy Spring Boot 2.1.4 / **Java 8** service that **parses inbound SendGrid email** to extract lead data (contact, vehicle, address) using DB-stored per-sender templates plus Jsoup HTML parsing, then forwards parsed leads to ShipperTMS via a raw `new RestTemplate()` call. Two endpoints: `/email` (SendGrid webhook) and `/parse` (QA testing). **The single most critical security / lifecycle flag in the fleet** — see Don't-do-here.

## How it fits
- Consumes API of: ShipperTMS (target URL not in code; inferred from runtime config). Inline `new RestTemplate()` — **no pool, no retries, no timeouts, no circuit-breaker**.
- Publishes events to: none observed.
- Subscribes to: none observed (no Kafka, no Pub/Sub, no Pub/Sub abstraction).
- Owns data store: **MySQL** via `mysql-connector-java` (legacy artifact id; replacement is `mysql-connector-j`). Connection params via env vars; `application.properties` is empty.

## Don't-do-here / gotchas (CRITICAL flags)
- **Spring Boot 2.1.4.RELEASE is EOL since May 2019.** Six years of CVEs unpatched (`spring-core`, `spring-web`, Tomcat embedded). This is the **#1 fleet-wide security/lifecycle finding**; the rest of the fleet is on 3.2.12.
- **Java 8** — EOL for OpenJDK public updates; only commercial vendors (Oracle / Adoptium) ship LTS patches. Modern dependency upgrades won't compile.
- **Raw `new RestTemplate()` inside the request path** — no pool, no timeout, no retry. A slow ShipperTMS hangs the parser thread on the default JDK socket timeout (effectively infinite). Replace with a configured `RestTemplate` bean or migrate to `WebClient`.
- **No error handling on the downstream call** — controller returns `200 OK` even when the ShipperTMS POST fails. SendGrid's webhook retry logic sees success and stops retrying; leads can be silently dropped.
- **`application.properties` is empty** — all config via env vars, no centralized config file. Audit is harder; misconfiguration is invisible until first request.
- **WAR packaging** — assumes a servlet container; doesn't fit the rest of the fleet's container-first pattern.
- **No structured logging, metrics, health checks, OpenAPI** — operational opacity.
- **No tests of consequence observed** — refactor risk is high.

## Recommended action
This service should be replaced or rewritten, not patched. The simplest forward path:
1. Freeze new feature work.
2. Stand up a Quarkus 3.27.0 successor with the same endpoints (the template-matching logic ports cleanly).
3. Run both in parallel behind a webhook splitter for one quarter to verify parity.
4. Decommission lead-parser.

Until then, **at minimum** wrap `RestTemplate` with `SimpleClientHttpRequestFactory` setting `connectTimeout=5000`/`readTimeout=10000` ms — that alone retires the hang-the-thread failure mode.
